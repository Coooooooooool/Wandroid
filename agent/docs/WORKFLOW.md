# Agent Development Workflow

## 1. 目标

本文档定义本项目的 Agent 开发流程，确保任务拆解、实现、验证和归档都可追踪。

## 2. 流程总览

标准流程：

```text
需求来源
-> 文档确认
-> 任务拆解
-> 状态登记
-> 实现
-> 验证
-> 文档回写
-> 任务归档
```

## 3. 阶段说明

### 3.1 需求来源

需求来源可以是：

- 产品目标
- `WANANDROID_API_CHECKLIST.md`
- 用户新增要求
- 已存在任务的衍生需求

功能开发要求：

- 每个需求都要能落到具体任务
- 未进入任务队列的需求，不直接开发

缺陷修复、UI 调整和范围明确的小型优化不创建独立任务。它们应直接实施，并在 `agent/docs/BUG_FIX_LOG.md` 中记录问题、改动、验证与遗留风险。

### 3.2 文档确认

开始功能任务前先检查：

- `PROJECT_SPEC.md` 是否覆盖该能力
- `MODULES.md` 是否已有结构约束
- `API_SPEC.md` 是否已纳入目标接口
- `TASK_QUEUE.md` 是否已有对应任务

若缺失，则先补文档，再开发。缺陷修复仅需确认相关模块和现有实现，不要求补充任务队列。

### 3.3 任务拆解

任务拆解规则：

- 一个任务只解决一个可验证目标
- 一个任务必须能在一次开发会话内形成明确增量
- 一个任务必须有验收标准
- 复杂能力按“页面入口、数据接入、交互动作”拆分

好的任务例子：

- 首页文章列表接入
- 首页 Banner 接入
- 登录会话持久化

不好的任务例子：

- 把所有接口都做完
- 完成整个 App

### 3.4 状态登记

功能任务进入执行前，必须在以下文件登记：

- `TASK_QUEUE.md`：记录任务定义、优先级、依赖
- `TASK_STATE.md`：记录当前状态
- 对应任务文件：记录范围和验收标准

缺陷修复、UI 调整和小型优化无需更新上述看板，完成后统一追加至 `BUG_FIX_LOG.md`。

### 3.5 实现

执行任务时遵守以下顺序：

1. 先搭接口和数据模型
2. 再写 Repository 和业务状态
3. 最后接 UI

如果任务只涉及文档或流程，则先更新规范文件，再同步任务状态。

### 3.6 验证

验证最少包括：

- 编译或静态检查
- 核对接口参数和分页规则
- 核对错误态、空态、加载态
- 与任务验收标准逐条比对

### 3.7 文档回写

完成后必须回写：

- 状态变更
- 范围变更
- 新增接口或新规则
- 风险与遗留项

功能任务回写任务状态和相关规范文档；缺陷修复回写 `BUG_FIX_LOG.md`。

## 4. 任务模板

每个任务文档至少包含：

- 背景
- 目标
- 范围
- 非范围
- 依赖
- 实现提示
- 验收标准
- 风险

## 5. Ready 条件

任务进入 `doing` 之前必须满足：

- 需求明确
- 依赖明确
- 接口已知或可确认
- 验收标准已写明

## 6. Done 条件

任务进入 `done` 之前必须满足：

- 功能实现完成
- 关键路径已验证
- 文档已同步
- 无未说明的阻塞项

## 7. 状态流转

统一状态流转如下：

```text
todo -> doing -> review -> done
todo -> blocked
doing -> blocked
blocked -> todo
```

状态含义：

- `todo`：已定义，未开始
- `doing`：正在实现
- `review`：实现完成，待复核或待验证
- `blocked`：存在外部阻塞
- `done`：完成并归档

## 8. 与 API 清单的关系

`WANANDROID_API_CHECKLIST.md` 是接口来源总表。

任务拆解时遵循以下原则：

- 先按业务能力分组，不按接口数量分组
- 一个任务可以覆盖多个紧密相关接口
- 只有进入近期计划的接口，才写入 `API_SPEC.md`
