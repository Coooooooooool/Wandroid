# UI 结构重规划建议

## 1. 文档目的

本文档用于重新规划当前 WanAndroid 客户端的界面信息架构。

它基于以下事实形成：

- 当前仓库已经接入的 API 能力
- 未来仍计划接入的 WanAndroid 功能
- 市面上内容类应用常见且合理的产品结构

这是一份产品与交互结构提案，不是直接的代码实现方案。

## 2. 当前结构存在的问题

现在的程序从“功能是否实现”角度看已经能工作，但它更像是“按任务拆页面”，而不是“按用户目标组织界面”。

主要问题如下：

- 一级入口过多，而且很多入口是按开发任务暴露出来的
- 页面分组依据更像 API 模块，而不是用户认知
- 登录、个人资料、积分、收藏，以及未来的消息和 TODO 被拆得过早
- 扩展内容是一个工程视角分组，不是用户视角分组
- 体系、导航、项目、搜索、扩展内容、个人页目前都像平级主页面，这不符合常见内容类 App 的导航结构

简而言之：功能已经有了不少，但应用还没有形成稳定的产品骨架。

## 3. 重规划原则

界面结构调整建议遵循以下原则：

1. 一级导航数量要少，而且长期稳定。
2. 页面分组应按用户目标，不按接口来源。
3. 所有登录态能力统一收拢到“我的”区域。
4. 所有内容发现类能力统一收拢到“发现”区域。
5. 所有文章阅读链路保持一致。
6. 不把“扩展内容”这种工程概念直接暴露给用户。

## 4. 建议的一层结构

建议采用 4 个底部主导航：

1. 首页
2. 发现
3. 项目
4. 我的

这样设计的原因：

- `首页` 是最高频回访页，应该承载最新内容流。
- `发现` 用来承接体系化浏览、社区内容和公众号内容。
- `项目` 是 WanAndroid 很明确的一类内容，值得独立成为一级入口。
- `我的` 是登录、资料、积分、收藏、消息、TODO 等个人能力的天然承载区。

这也是目前最贴近主流内容社区类应用的结构。

## 5. 推荐的导航模型

### 5.1 全局壳层

- 使用底部导航承载 4 个一级入口
- 每个一级入口保留自己的局部状态和返回栈
- 每个一级入口拥有自己的顶部栏
- 搜索不作为底部导航存在，而是从首页或发现页进入

### 5.2 二级导航

一级页面内部根据内容形式，使用以下方式之一：

- 顶部 Tab
- Chip 切换
- 吸顶分类切换
- 列表到详情的层级跳转

不要继续通过顶部菜单不断挂出新的 Activity 作为长期一级入口。

## 6. 各主页面结构建议

### 6.1 首页

目标：

- 快速浏览
- 高频回访
- 以阅读为主

内容建议：

- Banner
- 置顶文章
- 最新文章流
- 热门搜索词作为轻量入口
- 常用网站作为轻量入口

顶部操作：

- 搜索
- 可选的登录/头像入口

说明：

- 首页应该是“内容流”，不是“功能入口集合”
- 常用网站和热词可以作为首页模块存在，但不应被抬成重要主页面

### 6.2 发现

目标：

- 浏览不同来源、不同组织方式的内容

建议的内部栏目：

1. 体系
2. 导航
3. 问答
4. 广场
5. 公众号

原因：

- 这些能力本质上都是“继续找内容”
- 它们不需要各自拥有独立的产品一级地位
- 收拢到发现页以后，就不再需要“扩展内容”这个对用户并不友好的概念

各栏目的建议形态：

- `体系`：分类树 + 分类文章列表
- `导航`：分组推荐链接/文章
- `问答`：文章列表
- `广场`：社区分享文章流
- `公众号`：分类切换 + 文章列表

搜索位置：

- 发现页也应该可进入搜索，因为用户常常是在浏览分类或公众号内容后再搜索

### 6.3 项目

目标：

- 浏览项目类内容

建议内部结构：

1. 最新
2. 分类

行为建议：

- `最新`：展示最新项目文章流
- `分类`：展示项目分类 + 分类下项目列表

搜索：

- 项目/文章搜索建议作为顶部动作或页面内入口，而不是让“项目搜索”成为页面身份本身

原因：

- 当前实现把项目浏览和搜索绑定得太紧
- 从产品上看，项目页的中心应当始终是“项目内容”
- 搜索应该是动作，不应该压过项目页本身

### 6.4 我的

目标：

- 承载所有登录态和个人相关能力

建议结构：

- 顶部个人状态卡片
- 账户操作区
- 个人内容区

建议分区：

1. 账户
2. 我的内容
3. 工具与管理

建议功能项：

- 登录 / 退出登录
- 个人资料
- 积分
- 我的收藏
- 消息
- TODO
- 以后如果有设置或关于，也可以放在这里

重要说明：

- `我的` 页面即使未登录也应该存在
- 未登录时显示游客态和明确登录引导
- 登录页不应该长期作为一个“主模块”独立存在

## 7. 建议的页面层级

    搜索
    文章 Web 详情

  发现
    体系
      分类详情
      文章 Web 详情
    导航
      文章 Web 详情
    问答
      文章 Web 详情
    广场
      文章 Web 详情

      公众号分类文章流

    最新项目
    项目分类
    项目搜索

    游客态 / 登录态总览

## 8. 当前已实现功能如何映射

当前已经实现的页面，建议未来按以下方式重新归类：

- `HomeActivity` -> 首页 / 内容流
- `SystemNavigationActivity` -> 发现
- `ExtraContentActivity`
  - Wenda -> 发现 / 问答
  - Square -> 发现 / 广场
  - WeChat -> 发现 / 公众号
  - Latest Project -> 项目 / 最新
- `ProjectSearchActivity` -> 项目
- `AuthActivity` -> 我的 / 登录入口
- `CollectProfileActivity` -> 我的 / 收藏 + 资料
- `PointsActivity` -> 我的 / 积分
- `WebContainerActivity` -> 全局复用文章详情页

这意味着：现有实现其实大部分都能复用，问题主要不在功能缺失，而在页面编排方式需要调整。

## 9. 如果后续要重构，建议顺序

如果后续确认按这份提案重构，建议按以下顺序推进：

1. 先建立真正的主壳层和底部导航。
2. 把“体系 + 导航 + 扩展内容”重新归入发现页。
3. 把项目页拆成“最新”和“分类”，搜索作为动作保留。
4. 用真正的“我的”页替换当前“登录优先”的页面结构。
5. 把资料、收藏、积分、未来消息和 TODO 全部归入“我的”。
6. Web 详情页和收藏动作继续保持跨模块复用。

这个顺序对现有代码的冲击最小，但能逐步把产品结构纠正过来。

## 10. 为什么这个结构更适合 WanAndroid

WanAndroid 不是单一信息流应用，也不是纯工具应用。

它的能力天然可以归纳成 4 个用户目标：

- 看最新内容
- 找体系化或社区化内容
- 看项目内容
- 管理个人账户和个人能力

这正对应：

- 首页
- 发现
- 项目
- 我的

因此这套结构比当前“按任务拆入口”的方式更自然，也更容易长期维护。

## 11. 哪些内容不应该做成一级入口

以下能力不建议直接作为一级主入口对用户暴露：

- 登录
- 收藏
- 积分
- 扩展内容
- 问答
- 广场
- 公众号
- 导航
- 搜索

它们都很重要，但它们应该属于更大的用户任务流，而不是直接平铺在应用主结构上。

## 12. 预期结果

如果按这份结构调整，最终会得到这些收益：

- 一级入口更少，认知负担更低
- 用户更容易理解每个页面负责什么
- 后续接消息和 TODO 时不会再增加新的混乱入口
- API 分组和产品分组关系更清晰
- 应用整体不再呈现“工程任务清单式 UI”

如果认可这份提案，后续可以把它作为下一阶段 UI 重构任务的参考文档。
